1. Transport Layer Overview & UDP

Responsibility: Process-to-process delivery of the entire message using port numbers (16-bit).

  • Multiplexing: Gathering data from multiple app processes at sender.
  • Demultiplexing: Delivering data to correct app process at receiver.

UDP (User Datagram Protocol)

Characteristics

  • Unreliable Connectionless, No Flow/Error Control.
  • Header: Fixed 8 Bytes.
  • Use Cases: DNS, SNMP, RIP, Streaming (Real-time), Multicasting.

UDP Header (8 Bytes)

Source Port (16) Dest Port (16)
Length (16) Checksum (16)
Length includes Header + Data. Min value = 8.
Why use UDP if it's unreliable?

UDP avoids the overhead of connection establishment (3-way handshake) and maintaining state. It is preferred for applications where speed is critical (Voice over IP, Gaming) or where a lost packet is better ignored than retransmitted late.

Flags

  • SYN: Synchronize seq numbers (Connect).
  • ACK: Acknowledgment valid.
  • FIN: Terminate connection.
  • RST: Reset connection.
  • PSH: Push data (no buffering).
  • URG: Urgent pointer valid.

Wrap Around Time (WAT)

Time until Sequence Numbers (32-bit) repeat.

$$ WAT = \frac{2^{32}}{\text{Bandwidth (Bps)}} $$

Pseudo Header

Used for Checksum calculation. Includes Source IP, Dest IP, Protocol, TCP Length.

5. Flow Control & Window Management

Prevents sender from overwhelming the receiver using a Sliding Window Protocol. The window size is determined by the receiver (Advertised Window, $W_R$).

$$ \text{Effective Window} = \min(W_C, W_R) $$ Where \(W_C\) is Congestion Window and \(W_R\) is Receiver Window.

Silly Window Syndrome

Happens when data is exchanged in very small segments (e.g., 1 byte data + 40 bytes header), causing huge overhead.

Sender Side Solution Receiver Side Solution
Nagle's Algorithm
Accumulate data until:
1. A full MSS is available OR
2. An ACK is received for previous data.		 Clark's Solution
Advertise Window Size = 0 until:
1. Buffer has space for MSS OR
2. Buffer is 50% empty.

6. Error Control

Ensures reliability using Sequence Numbers, ACKs, and Retransmission.

Retransmission Triggers

  1. RTO Timer Expiry: Indicates severe congestion.
    • Action: Threshold = \(W_C / 2\), \(W_C = 1\), Slow Start.
  2. 3 Duplicate ACKs (Fast Retransmit): Indicates mild congestion (packet loss).
    • Action: Retransmit missing segment immediately without waiting for timer.

ACK Types

  • Cumulative ACK: "I have received everything up to N-1, expecting N".
  • Selective ACK (SACK): Explicitly lists received blocks (Optional).

RTT Estimation (Jacobson)

$$ \text{NewRTT} = (1-\alpha) \cdot \text{OldRTT} + \alpha \cdot \text{SampleRTT} $$

Typically \(\alpha = 0.125\).

Karn's Algorithm

Do not update RTT for retransmitted segments (ambiguity). Double the RTO (Exponential Backoff) on timeout.

8. Congestion Control

Sender maintains a Congestion Window (\(W_C\)).

Phase Behavior Condition
Slow Start Exponential Growth (\(W_C = W_C \times 2\) per RTT) \(W_C < \text{Threshold}\)
Congestion Avoidance Additive Growth (\(W_C = W_C + 1\) per RTT) \(W_C \ge \text{Threshold}\)
Congestion Detection Multiplicative Decrease Timeout or 3-Dup ACKs
New Threshold = Current Window Size / 2
Timeout? Set \(W_C = 1\), start Slow Start.
3-Dup ACKs? Set \(W_C = \text{Threshold}\), start Congestion Avoidance (Fast Recovery).

9. Traffic Shaping

Leaky Bucket

Concept: Turns bursty traffic into constant rate.

Mechanism: Input rate varies, output rate is constant. If bucket is full, packets are dropped.

Con: Cannot handle bursty data (idle time is wasted).

Token Bucket

Concept: Allows bursty traffic up to a limit.

Mechanism: Tokens generated at fixed rate. To send a packet, capture a token. Can send burst if tokens accumulated.

Formula: \( C + \rho \cdot t = M \cdot t \)
(Where \(C\)=Capacity, \(\rho\)=Token Rate, \(M\)=Max Burst Rate)
