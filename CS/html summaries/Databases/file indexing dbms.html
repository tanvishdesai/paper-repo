File Organization & Indexing

A comprehensive guide to storage strategies, indexing efficiency, and tree-based data structures.

1. File Organization & Blocks

Database records are mapped onto disk blocks. The efficiency of a database is often measured by the number of I/O Block Accesses required to fetch data.

graph LR A[Database] --> B[Files] B --> C[Blocks] C --> D[Records] D --> E[Fields]

Blocking Factor (\(B_f\))

The average number of records that can fit in a single block.

$$ B_f = \left\lfloor \frac{\text{Block Size } (B)}{\text{Record Size } (R)} \right\rfloor $$

Spanned vs. Unspanned Organization

Feature Unspanned (Preferred for Fixed Length) Spanned (Preferred for Variable Length)
Storage Record cannot span across blocks. Record can span across blocks.
Fragmentation Causes Internal Fragmentation (wasted space). No fragmentation (space utilized fully).
I/O Cost Lower I/O (1 block fetch per record usually). Higher I/O (May need 2 block fetches for 1 record).

File Access Methods

  • Unordered (Heap) File: Records placed in insertion order.
    Search Cost: Linear \(O(B)\) worst case, \(O(B/2)\) average.
  • Ordered (Sorted) File: Records sorted by a key.
    Search Cost: Binary Search \(O(\log_2 B)\).
    Drawback: Insertion is expensive (requires file reorganization).

2. Indexing Fundamentals

Indexing creates a separate auxiliary file to speed up data access, trading storage space for speed (reduced I/O).

Index Record Structure:
$$ \text{Index Entry Size} = \text{Search Key Size} (V) + \text{Block Pointer Size} (P) $$

Sorted small file] -->|Pointer| DataBlock[Data Block
Actual Record] DataBlock -->|Data| CPU

Dense vs. Sparse Index

Feature Dense Index Sparse Index
Entries One index entry for every search key in DB. One index entry for each block of data.
Size Larger file size. Smaller file size.
Speed Faster search (direct lookup). Slightly slower (find block -> scan block).
Requirement Can be built on ordered or unordered files. Must be built on an Ordered Field.

3. Types of Indexes

Indexes are classified based on the field they are built upon and the ordering of the data file.

graph TD Root[Index Types] Root --> Ordered[Ordered Field] Root --> Unordered[Unordered Field] Ordered --> PI[Primary Index
(Key + Ordered)] Ordered --> CI[Clustering Index
(Non-Key + Ordered)] Unordered --> SI[Secondary Index
(Key/Non-Key + Unordered)]
Detailed Breakdown of Index Types

1. Primary Index (PI)

  • Built on Ordering Key field.
  • Usually Sparse (One entry per block using Anchor Record).
  • Only 1 PI possible per file.

2. Clustering Index (CI)

  • Built on Ordering Non-Key field (records physically sorted by non-unique field).
  • Usually Sparse (One entry per distinct value/cluster).
  • Only 1 CI possible per file.

3. Secondary Index (SI)

  • Built on Unordered fields (Key or Non-Key).
  • Must be Dense (Because data file is not sorted by this field, we can't predict location).
  • Multiple Secondary Indexes are possible.
  • Used often for non-primary search keys (e.g., searching Employee by Name where ID is primary).

4. Multi-level Indexing

When an index file itself becomes too large to fit in memory, we create a sparse index on top of the index.

Access Cost:
$$ \text{Cost} = n + 1 $$ Where \(n\) is the number of index levels. 1 access for data block.
  • Base Level (Level 1): The original index file.
  • Outer Indexes: Sparse indexes pointing to the level below.
  • This process repeats until the top-level index fits into a single block.
  • This is the concept behind ISAM (Indexed Sequential Access Method) and B-Trees.

5. B-Trees (Balanced Trees)

A dynamic multi-level indexing structure that remains balanced (all leaf nodes at the same level). Suitable for disk-based storage.

Parameters (Order \(P\))

  • \(P\): Max number of Block Pointers (Children).
  • \(P-1\): Max number of Search Keys per node.
  • Nodes contain: \( [ P_1, K_1, R_1, P_2, K_2, R_2, ... P_q ] \) where \(R\) is Record Pointer.
Order Calculation Formula:
$$ P \times S_P + (P-1) \times (S_K + S_R) \le \text{Block Size} $$
Where:
  • \(S_P\): Size of Block Pointer
  • \(S_K\): Size of Key
  • \(S_R\): Size of Record Pointer

Node Constraints (Order \(P\))

Node Type Min Keys Max Keys Min Children Max Children
Root 1 \(P-1\) 2 \(P\)
Internal \(\lceil P/2 \rceil - 1\) \(P-1\) \(\lceil P/2 \rceil\) \(P\)
Leaf \(\lceil P/2 \rceil - 1\) \(P-1\) - -

6. B+ Trees

An improvement over B-Trees. Internal nodes serve only as an index (routing), while all data/records are at the Leaf nodes.

graph TD subgraph Internal Node I1[Key 10 | Key 20] end subgraph Leaf Nodes L1[Key 5 | Data] --> L2[Key 10 | Data] L2 --> L3[Key 15 | Data] L3 --> L4[Key 20 | Data] end I1 --> L1 I1 --> L2 I1 --> L4 L1 -.-> L2 L2 -.-> L3 L3 -.-> L4

Key Differences

B-Tree vs. B+ Tree Comparison
Feature B-Tree B+ Tree
Data Pointers In Internal AND Leaf nodes. Only in Leaf nodes.
Key Duplication Keys are unique (appear once). Keys in internal nodes are repeated in leaves.
Leaf Linking No links between leaves. Leaves linked (Linked List) for fast sequential access.
Range Query Slower (Must traverse tree up/down). Very Fast (Find start, then follow links).
Tree Height Higher (Record pointers consume space in internal nodes). Lower (More keys fit in internal nodes = higher fanout).
B+ Tree Order Calculations:
Internal Node (No Record Pointers): $$ P \times S_P + (P-1) \times S_K \le \text{Block Size} $$ Leaf Node (Contains Data Pointers): $$ (P_{leaf}-1)(S_K + S_R) + S_P \le \text{Block Size} $$

7. Summary & Key Takeaways

  • Optimization Unspanned organization is preferred for Fixed Length records (easier addressing).
  • Default B+ Trees are the industry standard for DB indexing due to efficient range queries and lower tree height.
  • Constraint At most one Primary or Clustering index is possible per file (since data can only be physically sorted one way).
  • Calculation Always use \(\lceil P/2 \rceil\) for minimum children calculation in trees.
