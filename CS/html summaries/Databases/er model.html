The ER Model & Relational Mapping

A comprehensive guide to Entity-Relationship modeling, Foreign Key constraints, and the algorithm for converting ER diagrams into Relational Tables (RDBMS).

1. ER Model Fundamentals

ER Model (Entity-Relationship Model): A high-level conceptual data model used to define data elements and their relationships for a specified system.

  • Entity An object in the real world that is distinguishable from other objects (e.g., a specific person).
  • Entity Set A collection of entities of the same type (e.g., all students). Represented by a Rectangle.
  • Weak Entity Set An entity set that does not have a primary key of its own. It depends on a Strong Entity (Owner). Represented by a Double Rectangle.

2. Attributes

Properties used to describe an entity. Represented by Ovals.

mindmap root((Attributes)) Simple ::Atomic values e.g. Roll No Composite ::Dividable e.g. Address > City, Pin SingleValued ::One value per entity e.g. Gender MultiValued ::Multiple values e.g. Phone Number ::Double Oval Stored ::Fixed value e.g. DOB Derived ::Calculated e.g. Age from DOB ::Dashed Oval Key ::Unique Identifier ::Underlined Text
Complex Attribute: A combination of Multivalued and Composite attributes (e.g., Multiple addresses where each address consists of Street, City, Zip).

3. Relationships & Cardinality

Relationship is an association among several entities. A Relationship Set is a set of relationships of the same type, represented by a Diamond.

Degree of Relationship

  • Unary: Relationship within the same entity set (Recursive).
  • Binary: Between two entity sets.
  • Ternary: Between three entity sets.
  • N-ary: Between N entity sets.

Mapping Cardinalities

Expresses the number of entities to which another entity can be associated.

Type Notation Description Visual Representation
One to One 1:1 An entity in A is associated with at most one entity in B, and vice-versa. \( E_1 \xrightarrow{1} R \xleftarrow{1} E_2 \)
One to Many 1:M An entity in A is associated with any number of entities in B. \( E_1 \xrightarrow{1} R \xleftarrow{M} E_2 \)
Many to One M:1 An entity in A is associated with at most one entity in B. \( E_1 \xrightarrow{M} R \xleftarrow{1} E_2 \)
Many to Many M:N Entities in A and B are associated with any number of entities from each other. \( E_1 \xrightarrow{M} R \xleftarrow{N} E_2 \)

4. Participation Constraints

Partial Participation

Not every entity in the entity set participates in the relationship.

Symbol: Single Line (—)

Total (Full) Participation

Every entity in the entity set must participate in the relationship.

Symbol: Double Line (==)

5. Foreign Keys & Integrity

A Foreign Key (FK) is a set of attributes in a table that refers to the Primary Key (PK) or Alternate Key of the same or another table.

graph LR A[Referencing Relation
(Child Table)] -- "FK points to" --> B[Referenced Relation
(Parent Table)] A -- "Contains FK" --> A B -- "Contains PK" --> B

Referential Integrity Operations

What happens to the Child (Referencing) table when we Delete/Update the Parent (Referenced) table?

1. On Delete/Update No Action

If the deletion/update violates integrity, the database rejects the operation. The parent row cannot be deleted if a child references it.

2. On Delete/Update Cascade

If a parent row is deleted, all corresponding rows in the child table are also deleted. (Use with caution).

3. On Delete/Update Set Null

If a parent row is deleted, the FK value in the child table is set to NULL. (Only valid if the FK column allows NULLs).

Note: Constraints are checked on the Referenced relation during Deletion/Update, and on the Referencing relation during Insertion.

6. ER to RDBMS Mapping Rules

This is the core algorithm for converting diagrams to tables. The goal is to minimize the number of tables while preserving data integrity.

Basic Entity Mapping

  • Strong Entity Set: Create a table. Columns = Attributes. PK = Entity Key.
  • Composite Attribute: Flatten into individual simple attributes (e.g., Name $\to$ FirstName, LastName).
  • Multivalued Attribute: Requires a separate table containing the Attribute + Foreign Key to the entity.

Relationship Mapping Logic

The number of tables required depends on cardinality and participation.

Relationship Type Mapping Strategy Min Tables (Binary)
1 : M (One to Many) Merge Relationship into the Many side table. 2
M : 1 (Many to One) Merge Relationship into the Many side table. 2
M : N (Many to Many) New Table required for Relationship (contains PKs of both entities). 3
1 : 1 (One to One) Merge Relationship into either side (prefer Total Participation side). 2 (can be 1 if Total Part.)

Summary of Minimization

  • If Total Participation exists on both sides (1:1, 1:M, M:1, M:N), theoretically 1 Table can suffice (though NULLs might be an issue in M:N or 1:M context, usually applies strictly to 1:1 or specific 1:M constructs). Standard Rule: 1:1 with Total Participation on both sides = 1 Table.
  • If Total Participation exists on ONE side (1:1), merge into that side = 1 Table.
  • Weak Entity Set: Always merge with the identifying relationship. Weak Entity Table includes its Partial Key + FK (Owner's PK).

Code Example: 1:M Mapping

Scenario: One Department has Many Employees. (Dept 1 --- M Emp)

/* Table 1: One Side */
CREATE TABLE Department (
    DeptID int PRIMARY KEY,
    DName varchar(255)
);

/* Table 2: Many Side (Merges Relationship) */
CREATE TABLE Employee (
    EmpID int PRIMARY KEY,
    EName varchar(255),
    DeptID_FK int,  /* Foreign Key moved here */
    FOREIGN KEY (DeptID_FK) REFERENCES Department(DeptID)
);

7. Transaction & Normalization Snapshots

Key concepts derived from the supplementary notes.

Weak Entity Design

A Weak Entity (e.g., Dependents of an Employee) must always be identified by the combination of its own Partial Key and the Primary Key of the Owner entity. It requires Total Participation.

Table Design: Dependent( Name, Age, Employee_SSN_FK ). PK is (Name, Employee_SSN_FK).

Self-Referential Relationships

An entity related to itself (e.g., Employee Supervised By Employee).
1:M (Supervisor-Subordinate): FK inside the same table.
M:N (Parts-Subparts): Separate table required.

Transaction & ACID
  • Atomicity: All or nothing.
  • Consistency: Database remains valid before and after.
  • Isolation: Transactions don't interfere.
  • Durability: Committed changes persist (survive crashes).
Recoverability Types
  • Recoverable Schedule: If $T_j$ reads from $T_i$, $T_i$ must commit before $T_j$ commits.
  • Cascadeless: $T_j$ only reads committed data.
  • Strict: $T_j$ neither reads nor writes data written by $T_i$ until $T_i$ commits/aborts.
