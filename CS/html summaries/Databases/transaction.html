A comprehensive synthesis of lecture notes covering ACID properties, Serializability, Concurrency Anomalies, and Protocols (2PL & Timestamp Ordering).

1. Transaction & ACID Properties

A Transaction is a unit of program execution that accesses and possibly updates various data items. It is a logical unit of work.

The ACID Paradigm

  • Atomicity
  • Consistency
  • Isolation
  • Durability
Atomicity: All or nothing. If it fails, rollback.
Consistency: Database remains consistent before and after transaction (e.g., sum of accounts).
Isolation: Transactions execute as if they are alone. handled by Concurrency Control.
Durability: Updates persist even after system failure. Handled by Recovery Manager.

3. Schedules

A Schedule is the order of execution of operations from multiple transactions.

Serial Schedule

Transactions are executed one after another (no interleaving).

If $N$ transactions: $N!$ possible serial schedules.

Always Consistent

Low Concurrency

Non-Serial (Concurrent)

Operations are interleaved to improve throughput and CPU utilization.

Total Schedules = $\frac{(N_1 + N_2 + ...)!}{N_1! N_2! ...}$

May be Inconsistent

4. Serializability

A concurrent schedule is Serializable if it is equivalent to some serial schedule.

1. Conflict Serializability

Most important for exams. Two schedules are conflict equivalent if the order of Conflicting Operations is the same.

Conflict Pair: Operations on the same data item by different transactions where at least one is a WRITE.

  • Read(X) - Write(X) Conflict
  • Write(X) - Write(X) Conflict
  • Read(X) - Read(X) No Conflict

Testing: Precedence Graph Method

Create a graph $G(V, E)$ where Nodes = Transactions.

  1. Draw edge $T_i \to T_j$ if $T_i$ performs an operation that conflicts with $T_j$ and $T_i$ comes first.
  2. Rule: If the graph has NO CYCLE (DAG), the schedule is Conflict Serializable.
  3. Ordering: The Topological Sort of the graph gives the equivalent Serial Schedule.
graph LR T1((T1)) -- R(A) then W(A) --> T2((T2)) T2 -- W(B) then R(B) --> T3((T3)) T3 -- Cycle --> T1 style T1 stroke:#f00,stroke-width:2px style T2 stroke:#f00,stroke-width:2px style T3 stroke:#f00,stroke-width:2px

Example: A cycle implies NOT Conflict Serializable.

2. View Serializability

Weaker than Conflict Serializability. Used when Blind Writes exist.

Check equivalence based on:

  1. Initial Read: Who reads the initial value of X?
  2. Updated Read: Who reads the value written by whom? ($W_i(X) \to R_j(X)$)
  3. Final Write: Who performs the last write on X?

5. Concurrency Problems

Issues arising when isolation is violated.

Problem Description Scenario
Dirty Read (WR) Reading uncommitted data. $T_1$ writes A, $T_2$ reads A, $T_1$ fails/rollbacks. $T_2$ has invalid data.
Unrepeatable Read (RW) Reading different values for same item. $T_1$ reads A. $T_2$ updates A. $T_1$ reads A again (different value).
Lost Update (WW) Overwriting updates. $T_1$ writes A. $T_2$ writes A (blindly) overwriting $T_1$'s work.
Phantom Read Variable number of rows. $T_1$ reads range. $T_2$ inserts new row in range. $T_1$ reads again (count changes).

6. Recoverability

Can the system recover to a consistent state if a transaction fails?

graph TD subgraph "Schedule Hierarchy" A[All Schedules] B[Recoverable] C[Cascadeless] D[Strict] A --> B B --> C C --> D end

Recoverable

If $T_j$ reads data written by $T_i$, then $T_i$ must commit before $T_j$ commits.

Issue: May lead to Cascading Rollback.

Cascadeless (ACA)

Avoids cascading rollbacks. $T_j$ can only read data written by $T_i$ after $T_i$ has committed.

No Dirty Reads.

Strict

If $T_i$ writes X, $T_j$ cannot Read OR Write X until $T_i$ commits/aborts.

Used in practical systems (Strict 2PL).

7. Lock-Based Protocols

Modes: Shared (S) for Read, Exclusive (X) for Write.

2-Phase Locking (2PL)

Transaction has two phases. Guarantees Conflict Serializability.

  1. Growing Phase: Acquire locks. Cannot release.
  2. Lock Point: Max locks acquired.
  3. Shrinking Phase: Release locks. Cannot acquire.

Variations of 2PL

Protocol Description Pros/Cons
Basic 2PL Standard grow/shrink rules. Ensures Serializability. Suffer from Deadlock & Cascading Rollback.
Strict 2PL Release all Exclusive (X) locks only after Commit/Abort. Ensures Recoverability & No Cascading Rollback.
Rigorous 2PL Release ALL locks (S & X) only after Commit/Abort. Easier implementation. Lower concurrency.
Conservative 2PL Acquire ALL locks before execution starts. Deadlock Free. High overhead.

8. Timestamp Ordering Protocol (TO)

Uses timestamps ($TS$) to determine serializability order (Older $\to$ Younger). No Deadlocks, but Starvation possible.

Variables

  • $TS(T_i)$: Timestamp of transaction.
  • $RTS(Q)$: Largest timestamp of any transaction that executed Read(Q).
  • $WTS(Q)$: Largest timestamp of any transaction that executed Write(Q).

Rule 1: $T_i$ requests Read(Q)

If $TS(T_i) < WTS(Q)$:

Reject & Rollback

(You are too old, value changed by younger)

Else: Execute Read

$RTS(Q) = \max(RTS(Q), TS(T_i))$

Rule 2: $T_i$ requests Write(Q)

If $TS(T_i) < RTS(Q)$ OR $TS(T_i) < WTS(Q)$:

Reject & Rollback

(Value read/written by younger transaction)

Else: Execute Write

$WTS(Q) = TS(T_i)$

Thomas Write Rule (Optimization)

A modification to standard TO for better concurrency (View Serializable).

Scenario: $T_i$ wants to Write(Q), but $TS(T_i) < WTS(Q)$.

Standard TO: Rollback.

Thomas Rule: Ignore the write (it's an "Obsolete Write" because a younger transaction already overwrote it). Continue $T_i$.
