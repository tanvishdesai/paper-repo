Deadlock in Operating Systems

Definition: A situation where a set of processes are blocked because each process is holding a resource and waiting for another resource acquired by some other process. It is an "infinite blocking" caused by a circular dependency.

Deadlock vs. Starvation
  • Deadlock: Infinite blocking. Circular wait involved. No progress possible.
  • Starvation: Indefinite blocking. Low priority process waits while high priority proceeds. Progress is happening for others.
System Model

Resources ($R_1, R_2... R_m$) and Processes ($P_1, P_2... P_n$).

2. Deadlock Characterization

Deadlock can arise if and only if these 4 necessary conditions hold simultaneously (Coffman Conditions).

1. Mutual Exclusion Resource

At least one resource must be held in a non-shareable mode. (e.g., Printer, Tape Drive). If another process requests it, it must wait.

2. Hold and Wait Process

A process must be holding at least one resource and waiting to acquire additional resources held by other processes.

3. No Preemption System

Resources cannot be forcibly taken from a process. A resource can be released only voluntarily by the process holding it.

4. Circular Wait Cycle

A set of processes $\{P_0, P_1, ... P_n\}$ exists such that $P_0$ waits for $P_1$, $P_1$ waits for $P_2$, ..., and $P_n$ waits for $P_0$.

3. Resource Allocation Graph (RAG)

A directed graph used to model the state of the system.

  • Vertices ($V$): Processes (Circles) and Resources (Rectangles).
  • Edges ($E$):
    • Request Edge ($P_i \to R_j$): Process asks for resource.
    • Assignment Edge ($R_j \to P_i$): Resource assigned to process.
Resource Type Cycle Presence Conclusion
Single Instance Cycle detected DEADLOCK (Necessary & Sufficient)
Multi-Instance Cycle detected MAYBE (Necessary but not Sufficient)
Any No Cycle NO DEADLOCK

4. Handling Strategies

1. Deadlock Ignorance (Ostrich Algorithm)

Pretend the problem doesn't exist. Used by Windows & UNIX. Why? Deadlocks are rare, and prevention is expensive.

2. Deadlock Prevention

Design system to invalidate at least one of the 4 necessary conditions. (Proactive)

3. Deadlock Avoidance

Allow requests only if the system remains in a "Safe State". Requires future knowledge (Max Need). (Banker's Algo)

4. Detection & Recovery

Let deadlock occur, detect it via graph/algo, and recover (kill process/preempt resource). (Reactive)

5. Deadlock Prevention

Ensure deadlock never occurs by breaking one of the conditions.

Attacking Mutual Exclusion

Method: Make resources shareable (e.g., Read-only files).
Problem: Not possible for all resources (e.g., Printers, Mutex locks intrinsic property is non-sharing).

Attacking Hold and Wait

Strategy 1: Request ALL resources before execution starts.
Cons: Low resource utilization, Starvation.

Strategy 2: To request a new resource, release all currently held resources first.

Attacking No Preemption

If a process requests a resource that is not available:
1. Release all currently held resources.
2. Preempt resources from the waiting process (if applicable).

Attacking Circular Wait (Most Practical)

Method: Assign a unique numerical number to each resource type. Require processes to request resources in increasing order of enumeration.

$$ \text{If } P_i \text{ holds } R_a \text{ and requests } R_b, \text{ then } F(R_b) > F(R_a) $$

6. Deadlock Avoidance (Banker's Algorithm)

Requires A Priori Information (Max Need). The OS runs the Safety Algorithm to check if granting a request leads to an Unsafe State.

Data Structures

  • \(n\): Number of processes, \(m\): Number of resource types.
  • Available \([m]\): Resources currently free.
  • Max \([n \times m]\): Max demand of each process.
  • Allocation \([n \times m]\): Currently allocated.
  • Need \([n \times m]\): Remaining need.
$$ Need[i,j] = Max[i,j] - Allocation[i,j] $$

Safety Algorithm Steps

  1. Initialize Work = Available, Finish[i] = false.
  2. Find a process \(P_i\) such that:
    • \(Finish[i] == false\)
    • \(Need_i \le Work\)
  3. If found:
    • Assume \(P_i\) finishes. Release its resources.
    • \(Work = Work + Allocation_i\)
    • \(Finish[i] = true\)
    • Repeat step 2.
  4. If all \(Finish[i] == true\), System is SAFE. If not, UNSAFE.
Resource Request Algorithm (When Pi asks for Request)
  1. If \(Request_i > Need_i\) -> Error (Process exceeded claim).
  2. If \(Request_i > Available\) -> Wait.
  3. Pretend to allocate:
    • \(Available = Available - Request_i\)
    • \(Allocation_i = Allocation_i + Request_i\)
    • \(Need_i = Need_i - Request_i\)
  4. Run Safety Algorithm. If Safe -> Grant. If Unsafe -> Rollback & Wait.

7. Detection & Recovery

Detection

Single Instance: Construct a Wait-for Graph (Remove resource nodes, collapse edges $P_i \to R \to P_j$ into $P_i \to P_j$). If Cycle $\exists \to$ Deadlock.

Multi-Instance: Use an algorithm similar to Banker's, but use \(Request\) instead of \(Need\). If processes remain unfinished $\to$ Deadlock.

Recovery
  • Process Termination:
    • Abort all deadlocked processes.
    • Abort one at a time (based on priority, cost, progress) until cycle eliminates.
  • Resource Preemption:
    • Select Victim (Cost minimization).
    • Rollback (Return to safe state).
    • Starvation (Ensure same victim isn't picked always).

8. Exam Formulas (Deadlock Freedom)

Common question type: "What is the minimum number of units of resource R required to ensure NO deadlock?"

Variables

  • \(N\): Number of Processes
  • \(K\): Max Need per Process (copies of resource R)
  • \(R\): Total Resources available
Deadlock Condition

Deadlock is possible if total resources are less than the sum of "Max Need - 1" for everyone.

$$ R < N(K-1) + 1 $$

(Worst case: Everyone holds K-1 and waits for 1)

Deadlock Freedom (Safe)

The system is guaranteed deadlock-free if:

$$ R \ge N(K-1) + 1 $$

General Formula (Different Needs)

If processes have different max needs ($Max_1, Max_2, ... Max_n$):

$$ \text{Deadlock Free if: } R \ge \left( \sum_{i=1}^{n} (Max_i - 1) \right) + 1 $$
